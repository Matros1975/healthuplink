Security

Last updated 25 November 2026

Health Uplink sends your Apple Health data from your iPhone to a receiver you run yourself. This page explains what protects that data on the way and where that protection ends, so you can judge the risk yourself. Not a medical device.

What there is to protect

  • Your health data: on the iPhone, in the phone's upload queue, on the network, and in the receiver's store and backups.
  • The device signing key: an Ed25519 key the app creates at pairing. It stays in the iPhone's Keychain on that device only and signs every batch and request.
  • The receiver's encryption key: an X25519 key in the receiver's data folder. The phone encrypts every batch to it.
  • MCP tokens: each agent's bearer token. The receiver stores only their SHA-256 hashes.
  • The pair token: a random 128-bit value in the QR code. It works once and expires after 10 minutes.

Protecting the link

Every connection from the phone to the receiver is encrypted and tied to the right server, in one of two ways:

  • Tailscale (WireGuard). Plain http:// is accepted only for addresses in the tailnet range 100.64.0.0/10, where WireGuard already encrypts the traffic and authenticates both ends. The app refuses plain HTTP to any other address, and the receiver's pair command refuses to print such a code.
  • TLS. Every other receiver needs https://. The certificate is either valid under the iPhone's normal trust store, or self-signed and pinned: the QR code carries the SHA-256 hash of the certificate's public key, and the app accepts no other key for that receiver. It never falls back to normal certificate checks or to HTTP. Pinning works only for IPv4 addresses, .local names and names without a dot, because iOS does not let an app replace normal certificate checks for an internet domain name; a receiver behind an internet name needs a certificate from a public certificate authority.

The pair token travels only over that protected link. If the receiver's certificate key changes, the app stops sending, keeps the data queued and says "Another device answered at …". It never pairs again by itself; you scan a new code.

What the batch encryption adds

On top of the link, the phone encrypts each batch with HPKE (X25519, HKDF-SHA256, ChaCha20-Poly1305) to the receiver's key, and signs it with the device key. Over a direct Tailscale link or a pinned TLS link, which already encrypt and authenticate, this adds little. It matters in three places:

  • Anything that ends TLS before the receiver. If you put a reverse proxy or a tunnel service in front of the receiver, the proxy sees the HTTP traffic, but the batches stay encrypted until the receiver opens them.
  • The queue on the phone. Batches wait in the app's outbox until they are delivered, sometimes for days. The outbox holds the batches only in encrypted form, and the app itself cannot open them again; only the receiver's key can. Next to each batch the app keeps its dates, type names and record count for the Sync activity screen, but no health values.
  • Forged or replayed batches. The batch ID, sequence number, device ID and key epoch are bound into the encryption as associated data and into the Ed25519 signature. The receiver accepts only batches signed by a paired device. A copied batch cannot be sent again under another batch ID, sequence number or device, and a batch received twice is stored once.

What it does not protect

  • The receiver itself. Whoever controls the receiver's machine, or gets a copy of its Docker volume or backups, can read everything: the store is not encrypted at rest, and the receiver's key sits in the same volume. Protect that machine and its disks as you would the data.
  • MCP tokens. Anyone holding a token can read everything the MCP tools return, which is all your synced data. Give each agent its own token and revoke tokens you no longer use.
  • AI providers. When an agent reads your data through MCP, the data goes into that agent's conversation. If the agent runs on a hosted model, the model provider sees what the agent reads, under that provider's terms.
  • A stolen receiver key. The receiver's key does not change with each batch. Someone who has recorded encrypted batches and later steals the key can open every batch sealed to that key. healthuplink keys rotate starts a new key; the old one is deleted about 30 days later, which limits how far back such a theft reaches.
  • Traffic analysis. Someone watching the network sees when the phone uploads and roughly how much, though not what.
  • A QR code on a compromised screen. The QR code decides which server the phone trusts. If the screen showing it is controlled by an attacker, the code can carry another server's address, key and pin, and the phone will send to that server.
  • The iPhone. The app reads Apple Health on the phone; anyone who controls the unlocked phone can read the same data there.

What Frontside does not do

Frontside Solutions runs no server for Health Uplink and receives none of your data. The app has no analytics, no crash reporter and no third-party code, and does not store health data in iCloud. Your data goes from your phone to your receiver and nowhere else, unless you connect an agent that sends it on.

How to check

  • The receiver in this repository is the code that runs on your server; read it, or build the image yourself from receiver/Dockerfile.
  • swift/HealthUplinkSeal is the package the iPhone app compiles for sealing, signing and pinning. It is the same code, not a copy.
  • contract/SPEC.md describes every message, and contract/vectors/ holds test vectors that both the receiver and the Swift package must pass, so each side can be tested against the other.

To report a vulnerability, see SECURITY.md or e-mail support@front-side-solutions.com with "SECURITY" in the subject.

Not a medical device. Health Uplink copies your Apple Health data to your server; it does not interpret it.
